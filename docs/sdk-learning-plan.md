# SDK 扩展学习计划

日期：2026-09-14

用户已确认继续学习 SDK，暂缓进入框架对照阶段。本计划在 P0–P4 基础上增加 E01–E13；E 表示扩展能力，不把这些能力全部称为 Agent Pattern。实际完成状态以 [任务清单](tasks.md) 为准。

## 推进原则

- 每次只完成一个小实验：先明确问题与边界，再实现、运行、回顾；一个学习项可以拆成多次对话，不设机械日程。
- 保留原有可运行例子，继续使用模型 SDK 手写调度。MCP 可使用协议 SDK，无需手写协议栈；这不等于迁移到 Agent 框架。
- Memory、MCP、Skill、Sandbox 均安排实际体验。依赖版本、服务能力和隔离环境在进入相应步骤时核实，不提前假定当前模型或 Windows 环境支持某项功能。
- 继续遵守项目约定：Pydantic 定义数据约束，Schema 集中管理；配置使用 .env 与 pydantic-settings，实例统一初始化；logly 记录执行，共用函数放入 tools/。
- 每步保留固定验收输入、受控失败场景和真实运行记录。调用次数、耗时、成功率分别记录，服务未提供 token 数据时标为不可用。

## 起点与先后顺序

P4 代码与离线验证已完成，真实运行与回顾仍待完成，不能因编写新计划而勾选。将其作为扩展前的短收尾；之后从 E01 的进程内会话开始。

| 顺序 | 学习项 | 分步实验 | 完成标准 |
| --- | --- | --- | --- |
| E01 | Memory：会话与持久记忆 | ① 同进程连续对话；② 按会话保存和加载历史；③ 单独保存用户明确提供的偏好，支持更新与删除 | 能承接上一轮；重启后恢复指定会话；不同会话不串话；偏好更新和删除生效 |
| E02 | 上下文管理 | 对同一长对话依次使用全量历史、最近几轮、历史摘要；为输入预留输出预算 | 展示实际送入模型的上下文；遵守预算；工具调用与结果成对保留；记录摘要遗漏或失真 |
| E03 | 评估与执行追踪 | 从 P1/P3/E01 选取 6–10 个固定案例；记录请求、工具、状态与独立验收结果；一次只改变模型或提示词一个变量 | 可重复运行并输出比较结果；流程完成与答案正确分开统计；不把模型自评当唯一标准 |
| E04 | 结构化输出 | 对比提示 JSON、本地 Pydantic 校验、服务支持时的结构约束；覆盖拒绝、截断和无效字段 | 正常数据能解析；无效数据明确失败；服务不支持时记录能力边界；合法结构仍需语义验收 |
| E05 | MCP：独立工具服务 | 将 add 放入本地 MCP 服务；客户端建立连接、发现工具、映射工具定义、执行并回传 | 完成真实发现与调用；观察未知工具、服务断开和调用失败；解释模型请求与 MCP 调用之间的适配 |
| E06 | Skill：按需加载说明 | 做两个本地技能目录，仅先提供名称与用途；按任务选择并读取完整说明及必要资源 | 选中技能可追踪；未选中内容不塞入上下文；能拒绝未知路径；说明不能自行扩大工具权限 |
| E07 | 人工介入与审批 | 用本地模拟账本展示付款参数；支持批准、拒绝和修改后重新确认 | 批准前无副作用；拒绝不执行；参数变更使旧批准失效；批准绑定具体操作 |
| E08 | 工具可靠性与幂等 | 模拟“执行成功但响应丢失”；为模拟操作加入持久幂等键与状态查询；设置有限重试 | 同一操作重试不重复记账；同键不同参数被拒绝；无法确认结果时标为未知，不当作失败重做 |
| E09 | 状态保存与恢复 | 保存执行阶段、操作 ID、工具结果和审批状态；在工具前后中断并重启 | 已确认成功的步骤不重跑；未决操作按 E08 查询；恢复待审批状态；解释崩溃窗口与保证范围 |
| E10 | Sandbox：受限代码执行 | 先选择并验证实际隔离机制，再运行固定简单代码；逐项验证文件、网络、时间和资源边界 | 正常代码完成；越界访问被实际阻止；超时进程被终止；不得把工作目录或普通子进程当安全隔离 |
| E11 | 检索与 RAG | 准备 3–5 份本地资料，先用简单检索选取片段再回答；之后再单独体验向量检索 | 答案能引用对应片段；无依据时说明不足；分别识别“没检索到”和“读到却答错”；向量实验独立对照 |
| E12 | 提示注入与信任边界 | 在测试文档、工具结果和技能资源中放入干扰指令；用虚构数据验证行为 | 记录是否被干扰；工具授权与审批由代码执行；越权动作无法执行；不宣称提示词能完全防御 |
| E13 | 流式响应与取消 | 先流式展示文本，再展示工具阶段事件；支持用户取消；最后处理工具执行中的取消 | 文本增量不重复；工具参数完整后才执行；取消后不启动新动作；已发生副作用明确报告而非假装撤销 |

E04 是对已有 JSON 清理与校验的深化。E01 的跨进程历史恢复和 E09 的执行恢复分开学习：前者恢复对话资料，后者决定能否继续执行有副作用的步骤。

关键依赖：E01 → E02；E07 → E08 → E09；E05/E06/E11 为 E12 提供不可信输入案例。E03 提前建立小型评估基线，随后各步只增补必要案例。E10 的隔离机制必须在执行模型生成代码之前验证。

## 案例如何延续

| 案例 | 使用范围 | 原因 |
| --- | --- | --- |
| 加法与简单学习助手 | Memory、上下文、评估、结构化输出、MCP、Skill、流式交互 | 沿用已有工具，减少业务变化 |
| 本地模拟账本 | 审批、幂等、执行恢复 | 有可观察的副作用，但不涉及真实付款 |
| 固定代码与临时数据目录 | Sandbox | 单独验证执行边界，不扩大主助手权限 |
| 少量本地示例资料 | RAG、提示注入 | 提供可人工核对的引用与干扰样本 |

不把全部能力一次性塞进一个主循环。出现明确复用需求时再提取工具函数，并保留旧实验用于对照。

## 每一步的交付与复盘

1. 短学习文档：问题、数据流、最小范围、失败条件。
2. 独立可运行入口与必要配置，具体目录在开始该步时决定。
3. 有针对性的离线测试及真实体验记录，未做的验证明确保留待办。
4. 用原始任务或程序可核对规则验收，记录收益、额外请求与新增失败点。
5. 更新 tasks.md，用户理解后再推进下一个学习点。

E13 后做一次 SDK 总回顾，再进入 Pydantic AI。原 P0–P4 仍是三个框架的共同对照基线；E01–E13 按实际收益选取框架对照项，不默认要求每个框架重做全部扩展实验。
