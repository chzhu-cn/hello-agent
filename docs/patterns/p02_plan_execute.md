# P2：先规划，再执行

## 学习目标与运行

让模型一次性给出步骤与依赖，由 Python 依次执行，再请求模型汇总。复用 add，P0/P1 继续保留。

```sh
uv run python -m hello_agent.sdk.p02_plan_execute.agent
```

默认计算 (127 + 358) + 96。计划示例：

```json
{"steps":[
  {"id":"first","tool":"add","a":127,"b":358},
  {"id":"second","tool":"add","a":{"step":"first"},"b":96}
]}
```

第二步引用 first 的真实结果，不需要模型先猜出 485。引用只能指向前面的步骤，禁止未知引用、循环和重复 ID。所有 Schema 在 schemas/planning.py，配置模型在 schemas/config.py，实例统一在 config/settings.py，工具复用 tools/arithmetic.py。

## 执行与调整边界

1. 模型按给定 JSON Schema 输出文本计划，Pydantic 在本地校验。这里不依赖服务端强制结构化输出，因此兼容服务可能返回无效 JSON。
2. 完整计划结构与步数通过校验后才开始执行。每一步解析引用后，仍需校验实际数字范围。
3. 执行记录包含步骤 ID 与真实结果，作为普通消息提交给模型汇总；这里没有使用 tool_calls 协议。
4. 无效计划在执行前最多修正 PLAN_MAX_REPAIRS 次（默认 1），用尽后停止。PLAN_MAX_STEPS 默认 5，限制计划中的工具步骤数，与 P1 的模型请求步数不同。
5. 工具执行失败、实际参数超范围、模型请求失败或不完整响应均停止。不进行执行中重新规划；已有结果不自动回滚。本例工具没有副作用。

计划校验保证结构可执行，不能保证模型正确理解任务。只支持加法，空计划允许普通问答，但不能凭空声称已执行计算。结构正确但语义错误的计划留给人工观察；P3 再学习检查结果。

正常路径两次模型请求（计划、汇总）；默认最多三次（含一次计划修正）。SDK 自动重试关闭。空计划仍需两次请求，因此简单问答可能比 P1 更费调用。

## 验证与对比

2026-09-13：全部 20 项离线测试通过（含 P0/P1）。P2 覆盖依赖解析和汇总载荷、有限计划修正、非法工具与引用拒绝、计划步数限制、空计划、重复 ID、工具失败不重复执行。

| 项目 | P1 | P2 |
| --- | --- | --- |
| 决策时机 | 每轮读结果后决定下一步 | 执行前生成完整计划 |
| 依赖传递 | 模型看到结果后生成参数 | Python 解析显式步骤引用 |
| 两次加法的正常请求次数 | 3 | 2 |
| 工具次数 | 2 | 2 |
| 调整策略 | 模型可每轮选择下一步 | 只在执行前修正无效计划 |
| 新增失败点 | 循环步数耗尽 | 无效计划、引用和语义错误 |

P1 上次真实运行约 6 秒（按日志时间粗略估算），不同时间服务延迟不一致，不据单次运行宣称性能优势。

学习问题：计划中的引用与 P1 的 tool_call_id 有什么区别？为什么合法 JSON 不一定是正确计划？执行中失败后，为什么不直接重跑整个计划？

真实验证：2026-09-13，gemini-2.5-flash 首次返回合法的 s1/s2 两步计划，s2 引用 s1。执行结果 485、581；最终回答正确。模型请求 2 次、工具执行 2 次，耗时 3.29 秒，无计划修正。沙箱初次连接失败，获准联网后成功。此例结构清晰、工具确定，适合预先规划；仍需用户完成学习回顾。
