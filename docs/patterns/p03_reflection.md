# P3：检查与修改

## 本步目标

案例、检查标准和停止条件已确定，最小实现与离线验证已完成，真实模型体验待完成。

P2 的结构校验不能保证结果符合用户要求。P3 增加一次针对已有答案的检查，再根据具体反馈修改。检查者仍可能出错，所以“模型说通过”与“实际验收通过”分别记录。

## 固定案例与检查依据

沿用任务：先计算 127 + 358，再将前一步结果加上 96；答案要求列出两步算式和最终结果。

本例先由 Python 调用共享 add 工具两次，得到 485 和 581，保存为事实依据。随后模型生成初稿、检查和修改。这里固定计算步骤，专注学习答案检查，不接入 P2 的自动规划；P2 保留独立运行。

检查时同时提供原始任务、真实工具记录和当前答案，按以下标准反馈：

1. 使用原始任务中的 127、358、96，没有偷换数字或遗漏步骤。
2. 第二步使用第一步的真实结果 485。
3. 两步算式分别为 127 + 358 = 485、485 + 96 = 581，最终结果为 581。
4. 答案列出两步算式和最终结果，且没有与工具记录矛盾的陈述。

例如初稿写成“485 + 69 = 554”，反馈应指出第二步将 96 写成 69，并引用任务和工具记录说明应改为 485 + 96 = 581。只说“答案不好，重新想想”不足以指导修改。

## 最小流程与边界

1. Python 执行两次 add，保存事实记录；失败则停止。
2. 请求模型根据任务和事实记录生成初稿。
3. 单独请求同一个模型检查，输出结构化反馈：passed 与 issues。issues 包含可核对的问题和修改建议，不要求隐藏推理。
4. 检查通过则结束；未通过且还有修改额度，则将任务、事实记录、当前答案和反馈交给模型修改。
5. 对修改后的答案再次检查；用尽额度仍未通过，明确标记“未通过检查”，保留最后答案与反馈。

默认最多修改一次，因此首次通过需 2 次模型请求；修改一次并复查需 4 次。工具始终只执行最初两次，修改答案不重新执行工具。修改上限为 0 时仍生成并检查初稿。

检查反馈用 Pydantic 校验：通过时 issues 必须为空，未通过时必须有问题。无效反馈、空响应或模型请求失败直接停止，不在本步叠加反馈修复循环。SDK 自动重试关闭。修改次数限制与 P2 的计划修正次数分别配置。

Schema 放在 schemas/ 下；配置使用 .env 与 pydantic-settings，实例统一在 config/settings.py 初始化；日志使用 logly。生成、检查、修改使用不同提示词，但本步不引入多 Agent 调度。

## 验收安排

| 场景 | 预期行为 |
| --- | --- |
| 初稿正确且检查通过 | 2 次模型请求，正常结束 |
| 初稿将 96 写成 69，收到具体反馈后修正 | 4 次请求，复查后结束；工具仍只执行 2 次 |
| 修改后仍未通过 | 达到上限后停止，明确报告未通过 |
| 修改上限为 0 | 生成和检查后停止，不发修改请求 |
| 无效检查反馈或模型请求失败 | 明确报告失败环节，不无限重试 |
| 检查者错误地放行错误答案 | 实际验收仍判失败，记录检查误判 |

受控响应验证错误修正和停止路径，避免要求真实模型偶然犯错。真实调用记录初稿、反馈、修改稿、请求次数、工具次数、耗时及人工按上述标准验收的结果。若真实初稿直接通过，如实记录，不能宣称观察到了修改带来的提升。

本例的计算可以直接由 Python 验证；增加模型检查是为了学习流程，其额外成本不代表该简单任务必须使用 P3。

## 学习问题

- 为什么检查者需要原始任务和工具记录，不能只看初稿？
- 为什么修改后还要再检查？
- 如果检查者说通过，但答案与工具记录矛盾，应相信哪一个？

## 真实运行与学习结论（2026-09-14）

用户提供的实验日志中，工具返回错误结果 486、583，原任务正确结果为 581。第一次运行修改了部分答案但仍错误，4 次模型请求、2 次工具执行、耗时 10.19 秒，最终达到修改上限。用户反馈增加额度也未修好。

本次展示了修正失败和误判通过。检查依据本身错误时，答案与工具记录一致不代表数学正确。增加修改次数或使用更强模型不保证解决依据冲突。Reflection 应配合明确标准和可靠的独立验证；本例应修正工具或验证计算，不能依赖反复改写答案。用户已完成本阶段学习回顾。
