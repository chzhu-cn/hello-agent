# P1：ReAct 风格循环

本步学习运行控制：模型根据工具结果继续决定下一步。只观察请求、工具和结果，不要求输出模型内部推理。P0 的固定流程保留。

## 运行

```sh
uv run python -m hello_agent.sdk.p01_react.agent
uv run python -m hello_agent.sdk.p01_react.agent "你好，请用一句话介绍自己"
AGENT_MAX_STEPS=1 uv run python -m hello_agent.sdk.p01_react.agent
```

默认任务：先调用 add 计算 127 + 358，拿到结果后再调用 add 加上 96。预期两次工具执行得到 485、581，再由模型回答。模型行为可能不同，需从日志确认确实连续调用。

## 流程与边界

入口为 `src/hello_agent/sdk/p01_react/agent.py`。`messages` 在一次任务中保留历史，每轮将 assistant 请求与全部 tool 结果追加进去。每次请求都允许模型自动选择是否使用工具。

- 无工具请求且正常返回非空文本：完成。
- 有工具请求：先校验整轮的名称、ID 和参数，再顺序执行并回传。
- 一步等于一次模型请求；`AGENT_MAX_STEPS` 从 `.env` 加载，默认 5，允许 1–100。
- 最后一步仍请求工具：达到上限，不执行没有剩余请求额度可回传的新工具。最后一步正常回答则成功。
- 未知工具、无效参数、缺失或重复 ID、工具执行失败、模型请求失败、空或截断响应：结束并报告原因，不自动修复或重试。

多个工具顺序执行时，如果后面的工具失败，前面的执行不会撤销。本例 add 没有副作用。步数限制约束模型请求次数，并不等同于工具调用总次数或总耗时限制；单次请求超时仍由 LLM_TIMEOUT 决定。

配置模型在 `schemas/config.py`，所有配置的模块级实例集中在 `config/settings.py`；工具 Schema 复用 `schemas/tools.py`。

## 验证与回顾

`uv run python -m unittest discover -s tests`：2026-09-13 共 13 项离线测试通过（含 P0）。P1 覆盖连续结果回传、直接回答、多工具 ID 关联、上限处不再执行、整轮校验失败不执行、工具失败、模型失败无重试、空与截断回答。

P0 用第二次请求的 tool_choice=none 结束固定流程；P1 每轮 auto，通过最终回答和最大步数结束。这使模型可以根据真实工具结果继续执行，也增加了请求次数和运行控制需求。

学习回顾：为什么两次连续工具执行通常需要三次模型请求？为什么上限处有工具结果不代表任务已经完成？一轮返回两个工具与连续两轮调用有什么区别？

真实验证（2026-09-13）：现有兼容服务的 gemini-2.5-flash 完成默认任务。第 1 步请求 add(127, 358)，结果 485；第 2 步请求 add(485, 96)，结果 581；第 3 步返回最终回答并正常退出。共两次工具执行、三次模型请求。首次沙箱连接失败，获准联网后成功。

工具复用：P0 与 P1 均导入 `hello_agent.tools.arithmetic.add`，不重复定义业务函数。
