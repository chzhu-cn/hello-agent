# P4：一次委派与返回

## 学习目标与范围

最小实现、离线验证及真实模型对比已完成，学习回顾待确认。沿用任务“先计算 127 + 358，再将前一步结果加上 96，列出两步算式和最终结果”，体验协调者将工作交给计算者，再接收结果回答用户。

第一版只有两个角色、一次委派、一次返回，顺序执行。两个角色可以使用同一个模型和 SDK 客户端，但使用不同系统提示词、独立消息历史和不同工具权限。Python 负责传递消息与控制流程；不需要多个进程或多个模型服务。

## 角色与权限

| 角色 | 职责 | 可用能力 | 上下文 |
| --- | --- | --- | --- |
| 协调者 | 理解任务、生成委派、接收结果、回答用户 | 委派给 calculator；不能调用 add | 原始任务、自己的委派及计算者返回结果 |
| 计算者 | 根据委派选择加法工具参数、连续计算、返回结果 | add；不能继续委派 | 原始任务、委派要求、自己的工具调用与结果 |

不同上下文与工具权限由代码实现，不仅靠提示词约束。计算者不能直接读取协调者的消息列表；共享任务通过明确字段传递。与 P3 的检查修改流程相比，本步增加独立的执行角色和交接边界，不添加检查者。

## 交接内容

协调者第一次模型调用生成如下委派对象，由 Python 用 Pydantic 校验：

```json
{
  "recipient": "calculator",
  "instruction": "先算 127 + 358，再把结果加上 96，返回两步计算记录。"
}
```

recipient 只允许 calculator，instruction 必须非空。Python 将原始任务原文连同委派传给计算者，防止仅靠转述丢失要求。结构校验不能保证委派语义正确，验收时仍要对照原任务。

计算者运行类似 P1 的工具循环：模型请求 add，Python 校验并执行，回传结果，再请求下一步。只有计算者能使用 add，工具结果由 Python 记录。

计算者结束后，Python 组装返回对象，包含：

- status：completed 或 failed，表示执行状态，不代表答案一定正确。
- answer：计算者的最终文本；失败时可以为空。
- records：实际执行的工具名称、参数及结果，不让模型伪造记录。
- error：失败原因；成功时为空。
- model_requests：计算者实际模型请求次数。

正常示例的 records 应包含 127 + 358 = 485、485 + 96 = 581。协调者接收返回对象后汇总；返回失败时 Python 直接明确报告原因，保留已有记录，不让协调者补猜答案。

## 流程与停止条件

1. 协调者生成一次委派，Python 校验；未知角色或无效委派直接停止。
2. Python 建立计算者独立消息历史，启动工具循环。
3. 计算者最多发起 5 次模型请求，计划使用独立配置 COOP_WORKER_MAX_STEPS。每轮最多允许一次 add 调用，超出则在执行前拒绝；工具参数由现有 AddArguments 校验。
4. 模型正常返回最终文本时结束计算者循环；无计算记录时不能作为本例计算成功返回。步数耗尽、非法工具或参数、工具失败、模型请求失败或不完整响应均返回失败，不自动重跑。
5. 成功后协调者再调用模型一次，依据原任务和返回记录汇总；汇总失败就报告失败，不重新启动计算者。

全程只允许一次委派，无递归委派或无限交接。SDK 自动重试关闭，继续复用请求超时配置。正常的两次连续加法预计为协调者 2 次请求、计算者 3 次请求，共 5 次模型请求、2 次工具执行；计算者上限为 5 时，全程最多 7 次模型请求。实际计数与停止原因必须记录。

首版只验收该固定计算案例，不增加动态路由、并行计算、任务队列或自动重试。

## 验收场景

| 场景 | 预期观察 |
| --- | --- |
| 正常两次加法 | 一次委派，两次 add，返回 485、581，协调者最终回答 581 |
| 上下文隔离 | 计算者仅接收明确传入的任务与委派；协调者接收返回对象，不共享同一个消息列表 |
| 未知接收者、无效委派 | 计算者未启动、工具未执行 |
| 非法工具、参数或同轮多个工具 | 拒绝无效调用，不执行该轮工具 |
| 工具中途失败 | 保留已有记录，返回失败，不重跑已成功步骤 |
| 计算者达到请求上限 | 明确返回失败，不进入成功汇总 |
| 协调者汇总请求失败 | 明确停止，不再次委派 |
| 注入错误工具结果 | 独立按算术验收判错；不能以协作完成代替正确性判断 |

先用受控响应验证交接和停止边界，再运行真实模型。错误工具结果作为单独故障实验，不混入正常路径；正常路径开始前确认共享 add 的结果正确。

对照 P1：相同任务和工具下，P1 两次连续加法通常需要 3 次模型请求，本例预计 5 次。新增收益是明确的职责、上下文和工具权限边界；新增成本是委派与汇总调用、转述遗漏和失败传播。记录实际调用数、耗时和结果，不预设多 Agent 更准确或更快。
