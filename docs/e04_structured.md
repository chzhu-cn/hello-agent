# E04：结构化输出的最小对照

运行：

```sh
uv run python -m hello_agent.sdk.e04_structured.agent
```

固定输入：“这件衣服是红色，但我最喜欢的颜色是青绿色。”提取 `favorite_color`，预期为青绿色。两次请求使用相同模型、系统提示和输入，只改变是否携带 `response_format`。

| 模式 | 请求 | 收到响应后 |
| --- | --- | --- |
| prompt | 提示词要求 JSON | Pydantic 校验 |
| schema | 相同提示词，加 json_schema / strict 参数 | 同样的 Pydantic 校验 |

Schema 放在 schemas/structured.py，拒绝额外字段，字段必填，值只接受字符串或 null。不清理 Markdown 围栏，不修补 JSON，直接验证原始正文；这样能观察原始输出是否符合约定。响应拒绝、截断、空正文或缺少 choices 时明确失败。

日志分别显示结构校验和事实验收，避免误把合法 JSON 当成正确答案。工具定义和结构化输出不同：这里没有工具执行，Schema 约束的是最终回答。请求错误不自动去掉参数重试，两种模式独立运行；任何失败最终退出码为 1。

当前兼容网关的行为需要实测。一次带 Schema 的成功请求只能说明本次接受请求并返回合法结果，不能证明网关内部一定启用了严格约束，也不能保证所有模型或 Schema 均支持。请求失败时记录 API 错误类型和状态码，不把所有错误都归因于不支持 Schema。

## 离线验证（2026-09-22）

新增 4 项测试，全套 90 项通过：合法字符串与 null；非法 JSON、缺字段、类型错误、额外字段、围栏与空正文；拒绝、截断和缺 choices；结构合法但事实错误。受控失败不代表真实服务本次出现同样问题。服务端约束不取代本地校验，事实仍需独立验收。

## 真实验证（2026-09-22）

当前配置下两次请求均成功：prompt 与 schema 模式均通过原始 JSON 的 Pydantic 校验，favorite_color 均为青绿色，事实验收通过。进程退出码 0，共 2 次模型请求、0 次工具执行；未统计 token、费用或精确耗时。

本次未观察到服务拒绝或截断，也未证明网关内部严格解码机制。学习重点是三个不同位置：提示词提出要求、请求参数传递结构要求、本地校验决定能否接受返回值。原始输入仍是事实验收依据。

## 学习回顾（2026-09-23）

同一输入下，`{"favorite_color":"红色"}` 可以通过当前 Pydantic 模型，却不符合原文；`{"favorite_color":3}` 则无法通过类型校验。字段的 description 帮助模型理解提取要求，不会让 Pydantic 自动判断颜色是否符合原文。只有衣服颜色、没有明确偏好时，预期为 `{"favorite_color":null}`。

本次修复的 SDK 类型标注服务于编辑器静态检查；response_format 将结构要求传给服务；Pydantic 在收到结果后做本地校验；事实验收判断是否符合任务。这四个环节作用不同。修复红线不会增加模型服务的能力。

本次仅补充回顾与进度记录，未修改业务代码，未重复调用模型或运行测试。用户理解确认仍保留待办；下一学习项为 E05：沿用 add，观察本地 MCP 工具发现与调用。
