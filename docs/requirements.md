# Hello Agent 项目需求文档

版本：0.2

日期：2026-09-12  
状态：学习目标与四阶段技术路线已确定；模型选型、具体案例和 Pattern 细节待讨论。

技术路线详见 [技术学习路线](technical-roadmap.md)。

## 1. 项目定位

Hello Agent 是一个以学习 AI Agent 开发为核心的 Python 实践项目。

项目通过逐步实现一个小型 Agent，理解模型调用、工具执行、上下文管理和运行控制，再使用不同框架实现相同能力，比较框架解决的问题、引入的抽象及适用场景。

学习主线：**亲手实现 → 理解问题 → 框架对照 → 判断取舍。**

项目不以快速搭建完整产品为首要目标。每一步应保持范围清晰、代码可读、行为可观察，能够解释原理并验证结果后，再进入下一步。

## 2. 学习目标

完成项目的核心学习阶段后，应能够：

1. 解释模型 SDK 与 Agent 框架各自承担的职责。
2. 使用模型 SDK，自行实现一个能够调用工具的 Agent。
3. 说明一次任务中，消息、工具调用参数和工具结果如何流转。
4. 理解 Agent 的继续执行、正常结束、异常退出和步数限制。
5. 识别实现过程中出现的上下文、校验、错误处理和状态管理需求。
6. 将框架提供的能力对应到手写实现，说明其收益与代价。
7. 根据实际需求判断何时手写、何时使用框架，以及如何选择框架。

## 3. 已确定的技术与学习原则

| 项目 | 决定 |
| --- | --- |
| 开发语言 | Python |
| 初始 Python 版本 | 3.14 |
| 项目与依赖管理 | uv |
| 版本管理 | Git |
| 第一阶段实现方式 | 使用模型厂商 SDK，手写 Agent 运行逻辑 |
| 技术路线 | SDK 手写 → Pydantic AI → LangChain → LangGraph |
| 推进方式 | 每条技术路线按同一份 Pattern List 逐个实现，再进入下一条路线 |
| 学习节奏 | 每次引入少量概念，先理解，再实现和验证 |

“手写 Agent”指自行实现消息管理、工具分发、结果回传和循环控制。模型请求使用现成 SDK，无需重新开发模型 SDK。

第一阶段保持直接、易读的代码结构。只有出现具体问题或重复代码时，再讨论封装与抽象。

## 4. 学习案例与交互范围

建议以一个小型命令行助手作为首个案例，便于直接观察输入、模型响应和工具执行过程。具体任务主题在接入模型前确定。

案例应满足：

- 至少包含一个结果可验证的 Python 工具。
- 能展示直接回答和调用工具两种路径。
- 后续可以扩展为连续调用工具的任务。
- 规模足够小，便于用不同框架重复实现并比较。

优先选择本地、确定性强、外部依赖少的工具，例如简单计算或读取专门准备的示例数据。工具的具体功能尚未确定。

各框架阶段应尽量沿用同一个案例、工具和验收任务，以便区分业务差异与框架差异。

## 5. 第一阶段：使用 SDK 手写 Agent

以下需求覆盖 SDK 阶段的基础调用、Agent 循环及基本可靠性。之后继续实现 Plan-and-Execute、Reflection / Critique 和多 Agent 协作，具体顺序及交付标准见 [技术学习路线](technical-roadmap.md)。各项逐步实现，不要求在一次开发中完成。

### 5.1 单次模型调用

功能要求：

- 配置模型、认证信息及必要的服务地址。
- 通过模型 SDK 发送一次输入并显示回复。
- 明确区分配置、用户输入与模型输出。
- 缺少必要配置时，给出可理解的提示。

验收标准：能够运行最小示例，获得真实模型回复，并说明请求与响应中的关键字段。

### 5.2 单次工具调用

功能要求：

- 定义一个 Python 工具及其名称、用途和参数说明。
- 将工具定义提供给模型。
- 识别模型返回的工具调用请求，解析参数并执行对应函数。
- 将工具执行结果关联到对应调用，回传模型，获得最终回复。

验收标准：完成一次真实的“模型请求工具 → Python 执行 → 结果回传 → 模型回复”过程，并能逐步解释数据流。

### 5.3 Agent 循环

功能要求：

- 在任务执行期间维护必要的消息历史。
- 支持多轮“模型调用 → 工具执行 → 结果回传”。
- 模型给出最终回答时结束运行。
- 设置明确的最大执行步数，达到限制时结束并说明原因。
- 正确处理一轮响应中返回的工具调用；初期可以顺序执行。

验收标准：直接回答的任务和需要连续调用工具的任务均能完成；达到步数上限时能够退出。

### 5.4 基本可靠性与可观察性

功能要求：

- 校验工具名称与参数，避免执行未注册的工具。
- 对模型请求失败、参数无效、工具执行异常等情况给出明确结果。
- 根据异常类型，明确选择结束运行或将错误反馈给模型，不无限重试。
- 展示执行步骤、工具名称、必要参数、执行结果及停止原因。
- 不在日志或版本库中记录认证密钥。

验收标准：正常路径及上述异常路径均有可重复的验证方式，能够根据执行记录定位失败环节。

执行记录用于观察请求、工具和状态，不要求获取或展示模型内部的隐藏推理。

## 6. 后续阶段：框架对照学习

SDK 阶段按 Pattern List 完成学习后，依次使用 Pydantic AI、LangChain、LangGraph 逐个实现相同的学习项。各阶段结合手写时遇到的问题进行对照。

| 框架（按实施顺序） | 对照学习重点 |
| --- | --- |
| Pydantic AI | 类型、结构化输出、参数校验与依赖传递如何融入 Agent 开发 |
| LangChain | 模型和工具接口、Agent 运行及组件集成如何减少重复实现 |
| LangGraph | 状态与执行流程如何表达，以及如何处理分支、中断和恢复 |

每引入一种框架，应完成：

1. 明确本次希望解决的具体问题。
2. 用该框架实现已有案例的可比功能。
3. 运行与手写版相同的核心验收任务。
4. 对照手写版，记录减少的代码、增加的概念及行为差异。
5. 总结适用场景、限制和选择理由。

对比时尽量保持模型、提示词和工具一致；无法保持一致的地方应记录原因。模型输出不要求逐字一致，应比较任务完成情况、工具行为及错误处理。

框架迁移时保留可运行的手写学习基线。具体通过目录还是 Git 版本保留，在迁移前决定。

## 8. 验证与学习记录

首阶段至少覆盖以下场景：

| 场景 | 预期行为 |
| --- | --- |
| 无需工具的输入 | 返回答案并正常结束 |
| 需要一个工具的输入 | 执行工具并依据结果回复 |
| 需要连续工具调用的输入 | 传递前一步结果，继续执行至结束 |
| 未知工具或无效参数 | 明确报告问题，不执行无效调用 |
| 工具函数失败 | 记录失败并按已定义策略处理 |
| 达到步数上限 | 停止运行并说明原因 |
| 模型请求失败 | 给出可定位的错误信息 |

真实模型调用用于验证端到端行为；工具校验、异常和停止条件可通过受控响应验证，避免依赖模型偶然产生错误。

每个学习步骤应记录：新增概念、运行方式、观察结果，以及当前仍存在的问题。文档详略以能帮助复现和理解为准。

## 9. 当前不纳入的范围

以下能力暂不作为第一阶段要求，出现明确学习需求后再讨论：

- Web 界面与服务部署。
- 知识库、向量数据库与 RAG。
- 长期记忆和跨进程会话恢复。
- MCP、浏览器自动化或任意代码执行。
- 模型训练与微调。
- 通用 Agent 框架开发。
