# E02-A：全量历史与最近几轮

## 本步问题

保存下来的历史，不一定全部进入本轮模型请求。本实验只比较两种选择方式：全量历史与最近 N 个完整文本轮次。暂不实现摘要、token 预算、工具消息或交互会话管理。

使用人工预置的四轮对话：第一轮明确说明“我最喜欢青绿色”，后面三轮为无关话题；最后追问最喜欢的颜色。预置助手回复不是实时生成的。两个策略共享同一份原始历史、系统说明、问题与模型配置，各请求一次；第一个回答不会放入第二个请求。

## 运行

```sh
# 仅查看实际请求消息，不请求模型
uv run python -m hello_agent.sdk.e02_context.agent --preview

# 两次真实模型请求进行对照
uv run python -m hello_agent.sdk.e02_context.agent
```

沿用现有 LLM 配置。`.env` 中 `CONTEXT_RECENT_TURNS=2` 表示窗口保留最后两轮，一轮是一条 user 加一条 assistant。范围为 0–100，0 表示不带历史，超过历史轮数则保留全部。配置实例在 settings.py 统一初始化，预览也要求项目配置有效。

可把窗口改成 4 后再次预览：此时窗口与全量策略携带的消息相同，第一轮偏好重新进入请求。

## 数据流与观察

`Conversation → build_messages → 系统说明 + 选中历史 + 当前问题 → request_text`

窗口切片只产生请求副本，不删除或改写原始历史；系统说明和当前问题始终保留。当前数据模型只接受完整的 user/assistant 文本轮次，不支持工具调用消息。未来工具上下文需要另外处理调用与结果的关联，不能直接套用两条消息为一轮的规则。

日志逐条显示实际发送的角色、正文，以及原始轮数、发送轮数、总消息数和正文字符数。字符数不等于 token 数，也不是输入预算；按轮数裁剪不能保证请求不超出模型上下文限制。

默认全量发送 10 条消息，窗口发送 6 条。全量含偏好依据，预期回答青绿色；窗口不含依据，预期回答不知道。依据缺失是确定的请求事实，但模型回答仍需观察，不能把偶然猜对当成成功恢复记忆。

请求失败不重试，继续另一项独立对照；任一请求失败最终退出码为 1。问答不写入原始历史或磁盘。固定示例使用虚构信息，日志会展示其完整正文。

## E02-B：旧历史摘要（2026-09-17）

窗口丢弃早期信息，本步尝试把早期内容压缩成摘要再带入请求。运行：

```sh
uv run python -m hello_agent.sdk.e02_context.summary
```

沿用 E02-A 同一份四轮预置对话、模型、系统说明和最终问题。先分别请求全量、窗口回答，然后调用模型摘要窗口外的旧历史，再以摘要与最近完整轮次请求回答。默认窗口为 2 轮，总共 4 次模型请求：全量 1、窗口 1、生成摘要 1、摘要策略回答 1。没有旧历史时跳过摘要请求，整个对照仅需 3 次请求。

摘要输入仅包含旧历史，不包含最终问题、近期对话或其他策略的回答。输出作为标明来源的 user 数据消息插入，未升级为系统指令。日志展示摘要来源、生成的摘要、最终请求、正文字符数和耗时。摘要失败则停止该策略，不自动重试，也不退回全量原文假装摘要成功。原始 Conversation 不变，无磁盘持久化、递归摘要、工具消息或预算限制。

本步观察三个问题：偏好是否保留、其他事实是否遗漏或写错、摘要是否真的更短。提示要求尽量简短，但没有硬性长度限制；对很短的原文，摘要及其标签可能使最终输入更长。字符数不是 token，摘要请求本身也有成本，不能仅凭最终消息数减少就判断省钱。

### 离线验证

新增 5 项测试，全套 71 项通过。验证摘要只接收旧历史、不污染原始记录、零窗口摘要全部、无旧历史跳过请求、空摘要失败。另注入两份受控摘要：一份遗漏颜色，一份把颜色写成红色。两者都能通过非空文本检查，最终请求不再含原来的青绿色；代码不会自行纠正语义错误。这是受控失败场景，不表示真实模型本次发生了同样错误。

摘要是模型对历史的有损转述，不能用“成功返回文本”代替事实验收。真实运行需把摘要与原文逐项对照，再看最终回答。

### 真实结果（2026-09-17）

使用当前 gemini-2.5-flash、窗口 2 轮，共 4 次模型请求，进程正常退出。

| 策略 | 回答请求正文字符数（非 token） | 回答 | 耗时 |
| --- | --- | --- | --- |
| 全量 | 147 | 青绿色。 | 3.03 秒 |
| 最近两轮 | 92 | 不知道。 | 1.54 秒 |
| 摘要＋最近两轮 | 162 | 青绿色。 | 3.45 秒，含生成摘要 |

模型生成的摘要原文：

```text
- 用户偏好：最喜欢的颜色是青绿色。
- 未完成事项：练习加法（2+3=5已由助手回答）。
```

颜色偏好保留正确，最终回答通过颜色问题验收。但原文并未要求继续练习，加法问题也已经回答；摘要将它归入“未完成事项”缺乏依据，是本次真实观察到的状态失真。未发现颜色或算式丢失，不能因此认定摘要整体准确。

旧历史正文 55 字符，摘要 45 字符；加上摘要来源标签后，最终请求反而比全量长 15 字符。未统计 token 或费用，不宣称节省成本；单次耗时不代表稳定性能。学习回顾待用户体验，本次不推进预算控制。

## E02-C：本地估算预算与输出预留（2026-09-17）

```sh
uv run python -m hello_agent.sdk.e02_context.budget --preview
uv run python -m hello_agent.sdk.e02_context.budget
```

第一条只检查预算并显示请求；第二条发送一次模型请求。沿用 E02-A 的预置四轮文本，不把摘要生成请求纳入本实验。

`.env` 配置：

```dotenv
BUDGET_CONTEXT_TOKENS=640
BUDGET_OUTPUT_TOKENS=128
BUDGET_SAFETY_TOKENS=64
```

输入估算预算 = 总预算 − 输出预留 − 安全余量，默认 448。总预算是实验自设额度，不代表模型的真实上下文容量。配置由 BudgetConfig 校验，在 settings.py 统一初始化。

本地启发式为：正文 UTF-8 字节数之和 + 每条消息 16 + 请求固定 3。它不是 Gemini tokenizer，不是服务 token 数的保证上界；安全余量也不提供这种保证。这里严格遵守的是**本地估算额度**，尚不能保证任意服务的真实 token 输入预算。Google 提供单独的 [countTokens 接口](https://ai.google.dev/gemini-api/docs/tokens)，本项目当前兼容网关未接入或验证该接口，也未借用其他模型 tokenizer 冒充 Gemini 精确计数。

从全量开始，超预算就移除最早的一整轮 user/assistant；系统说明、当前问题不删。如果仅这两条仍超预算，则在请求前明确失败。原始历史不变。这里不处理工具调用、摘要来源、图片或其他多模态开销。

将输出预留作为 `max_tokens` 传给兼容接口，响应中记录 usage。服务拒绝参数时明确失败，不去掉限制自动重试；输出被截断（finish_reason=length）沿用共用校验报错，不把半句当完整回答。单次正常短回答不能证明服务必然执行输出上限，需区分已发送限制与硬上限保证。

### 离线验证

新增 6 项测试，全套 77 项通过：预算边界恰好容纳、少 1 单位裁掉完整轮次、原始历史不变、仅固定消息仍超预算、配置约束、多字节文本估算、输出参数传递与旧调用不受影响、截断响应失败不重试。

### 真实与预览验证（2026-09-17）

当前模型 gemini-2.5-flash，输出预留 128、安全余量 64；仅在验证进程覆盖总预算，不修改用户 `.env`。

| 总预算 | 输入估算额度 | 保留轮数 | 实际本地估算 | 服务 prompt_tokens / completion_tokens | 结果 |
| --- | --- | --- | --- | --- | --- |
| 640 | 448 | 3 | 448 | 83 / 2 | 不知道。 |
| 1000 | 808 | 4 | 576 | 107 / 3 | 青绿色。 |
| 200 | 8 | 无法容纳固定消息 | 未发送 | 无请求 | 预览明确拒绝 |

两次真实请求成功且正常结束。第三项仅运行本地预览，固定输入超预算时拒绝，未调用模型。共 2 次真实请求，未统计费用。服务返回兼容字段 prompt_tokens 与原生 promptTokenCount 一致；其他扩展字段 input_tokens 为 0，因此不将其作为输入统计。

本例估算远大于实际报告，带来过早裁剪；记录这个局限，不把估算器称为精确计数或通用上界。E02-C 仍保留学习回顾与精确计数待办，整个 E02 尚未完成。
