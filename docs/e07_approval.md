# E07-A：人工审批与本地模拟账本

## 本步要理解的问题

此前 add 只返回计算结果。换成有副作用的动作，就需要在执行前停下来，让人查看具体参数并作出决定。本步先用固定模拟付款学习这道审批检查，不调用模型、不接真实支付服务。

```sh
uv run python -m hello_agent.sdk.e07_approval.local
```

默认提案是向“示例供应商 A”模拟支付 125.00 CNY，用途为“模拟购买学习资料”。程序展示提案 ID、收款人、金额、币种、用途和当前账本笔数，然后等待输入：

- `a`：批准当前显示的提案，再执行模拟记账。
- `r`：拒绝，结束本次运行，账本仍为零笔。
- `m`：输入新的收款人、金额和用途，再展示新提案，等待重新确认。
- 输入结束或 Ctrl+C：拒绝当前待处理提案。

金额输入使用整数分，例如 9900 表示 99.00 元；不使用浮点金额。内存账本在退出后消失。

## 批准到底绑定什么

`PaymentArguments` 保存收款人、金额、币种和用途；`PaymentProposal` 保存参数与唯一 ID。它们都是冻结的 Pydantic 模型，避免普通赋值绕开修改流程。

`PaymentApproval` 保存当前提案和审批状态：

```text
pending → approve(当前提案 ID) → approved → execute() → executed
   └──→ reject(当前提案 ID) → rejected

pending / approved → revise(新参数) → 新 ID、pending、清除旧批准
```

审批不等于执行：`approve()` 只记录批准，`execute()` 才写入账本。命令行的 `a` 连续调用这两步；执行函数仍独立检查当前状态和批准的提案 ID。

执行时不重新接收一份付款参数，而是使用已批准提案中的参数。即使已经批准过，只要修改收款人、金额或用途，就会创建新 ID，并要求重新批准。拿旧 ID 来批准会被拒绝。已拒绝或已执行的审批不能重新执行。

## 代码位置

- `schemas/approval.py`：付款参数、提案、审批状态、账本记录。
- `tools/approval.py`：审批检查与内存模拟记账。
- `sdk/e07_approval/local.py`：展示参数并读取人工决定。

下一小步才让模型生成付款提案。模型只提出参数，不持有批准入口；审批决定仍来自人工交互。

## 验证（2026-09-23）

```sh
uv run python -m unittest discover -s tests -p "test_approval.py"
```

7 项测试通过：未批准不得执行、批准本身不记账、单次执行、拒绝后不执行、逐字段修改使批准失效、旧 ID 与无关 ID 被拒绝、冻结参数不能直接赋值、修改后批准、非法输入与输入结束不批准，以及非法金额/收款人校验。

使用命令行管道分别运行批准、拒绝、修改后批准：账本结果分别为 1 笔、0 笔、1 笔；修改后的记录为 99.00 CNY 与新收款人。此为自动输入的真实本地进程验证，不等于用户手动体验。未请求真实模型、未重跑全套测试。

本步仅限单进程、串行、内存操作。结束状态防止同一审批对象重复执行，不是跨进程幂等保证；未实现持久化、崩溃恢复、身份认证或并发审批。相关问题按 E08/E09 分步学习。
