# E06：按需加载技能说明

## 本步要理解的问题

有些任务需要专门的操作说明，但每次请求都携带全部说明会增加上下文。这里学习先展示技能名称与用途，再按任务加载选中技能的正文和必要资源。

这是本项目自己的最小学习实现，不依赖某个平台的技能加载机制。

## 最小案例

准备两个本地技能目录：

| 技能 | 用途 | 按需资源 |
| --- | --- | --- |
| addition-guide | 指导助手使用已有 add 工具完成加法并说明结果 | 算式展示示例 |
| learning-review | 按固定结构整理一个学习概念 | 回顾模板 |

每个目录包含技能说明及资源。另用清单登记名称、用途和允许读取的文件；发现阶段只读取清单，不读取全部正文。

## 数据流

1. 向模型提供任务及技能名称、用途。
2. 模型选择一个技能名称，也可以选择不使用技能。
3. 程序校验名称，只从登记的目录加载对应说明。
4. 按需加载该技能清单中登记的资源，记录实际加载项。
5. 将选中内容加入本次请求，由模型完成任务。

选择结果用 Pydantic 校验；文件加载逻辑放在 tools，数据模型放在 schemas。先做本地发现与加载，再接模型选择，避免一次引入过多变化。

## 权限边界

技能正文是操作说明，不是授权来源。可用工具仍由程序决定，技能不能通过声明增加工具权限，也不自动执行技能目录中的脚本。

外部输入只能选择登记的技能和资源名称，不能提交任意文件路径。读取前解析实际路径并检查仍位于允许目录中；拒绝未知名称、路径穿越及指向目录外的链接。这只是加载器的读取约束，不是操作系统沙箱。

## 验收与进度

- [x] 只加载选中技能的说明，资源按需读取。

- [x] 未知技能、未知资源、绝对路径及父目录跳转被拒绝。

## E06-A 本地体验（2026-09-23）

已实现独立入口，使用随示例保存的固定技能目录，不依赖模型配置：

```sh
# 只展示目录，不读取正文或资源
uv run python -m hello_agent.sdk.e06_skill.local

# 加载加法指导正文，不自动加载资源
uv run python -m hello_agent.sdk.e06_skill.local addition-guide

# 加载正文及指定资源
uv run python -m hello_agent.sdk.e06_skill.local addition-guide --resource example
uv run python -m hello_agent.sdk.e06_skill.local learning-review --resource template

# 运行加载器验证
uv run python -m unittest discover -s tests -p "test_skills.py"
```

文件位置：`sdk/e06_skill/skills/catalog.json` 登记名称、用途与资源映射；两个技能目录保存正文及资源。`schemas/skills.py` 定义 Pydantic 数据模型，`tools/skills.py` 中的 SkillStore 负责发现和加载。

`discover()` 只返回名称与用途；`load(name)` 返回正文和可用资源名称；`load_resource(name, resource)` 才读取指定资源。日志记录实际读取的技能和资源文件。这里的 SKILL.md 是学习程序的数据，不会自动注册成 Codex 技能。

验证结果：4 项自动测试通过，覆盖实际文件读取顺序、未选中内容不读取、未知名称拒绝、登记路径越界拒绝、缺失资源不影响发现和正文加载；1 项真实符号链接测试因 Windows 创建权限不足跳过。已运行只发现目录、两个技能及其资源的加载；未知技能输入以退出码 1 拒绝。

目前没有向模型发送上下文或执行工具，相关验收留到 E06-B。解析实际路径后的检查用于防止普通越界读取，不是对恶意并发修改文件系统的隔离保证。

## E06-B 模型选择（2026-09-23）

```sh
uv run python -m hello_agent.sdk.e06_skill.agent
uv run python -m hello_agent.sdk.e06_skill.agent "请使用加法技能计算 127 加 358，并参考算式展示示例。"
```

使用现有模型配置与共用请求函数。首次请求仅提供任务、技能名称和用途，Pydantic 校验模型选择；选择 null 时不加载技能。选中后读取说明，第二次请求让模型选择必要资源，支持空列表。校验资源名称后才读取文件，第三次请求使用原始任务及已选说明和资源完成回答。

执行阶段固定只提供 add 工具。需要调用时最多执行一次，再发送一次请求总结，因此无技能路径需 2–3 次请求，有技能路径需 3–4 次请求。不自动重试无效选择，不执行技能目录里的代码。选择阶段只用提示要求 JSON，再本地校验，没有声称服务提供严格结构约束。

新增 5 项受控测试：技能与资源的分阶段上下文、加法执行和结果关联、不选技能、不选资源、未知选择拒绝，以及技能声称授权 shell 时仍拒绝执行。Skill 相关共 10 项测试，9 项通过，1 项真实符号链接测试仍因环境权限跳过。未重跑全套测试。

这里验证的是程序工具权限不被扩大，不代表模型文字回答不会受技能内容干扰；提示注入实验留在 E12。

### 真实体验结果

使用当前配置的 gemini-2.5-flash，两个入口均正常退出：

| 任务 | 技能与资源 | 请求数 / 工具执行数 | 结果 |
| --- | --- | --- | --- |
| 127 加 358，参考展示示例 | addition-guide / example | 4 / 1 | 实际 add 返回 485.0，最终回答 127 + 358 = 485 |
| 回顾 MCP，使用回顾模板 | learning-review / template | 3 / 0 | 按概念、例子、易错点回答，解释 MCP 是通信规范 |

回顾任务验证了技能选择与输出结构，没有做全面知识评估。其中“无需为每个工具编写专用集成代码”的表述过于概括：工具实现仍需服务端提供，客户端仍需模型适配。这也说明加载技能不能保证回答中的每个事实都准确。

### 学习回顾与用户实测（2026-09-23）

用户指出当前流程是固定 workflow，并明确继续按步骤学习，不改成动态 Agent 循环。该实现由程序决定选择、加载和执行顺序，模型在每一步内选择内容。

用户输入“67 * 98等于多少”，日志显示未选技能，随后调用 add(a=6700, b=-134)，最终回答 6566。参数对应正确的分解 67×(100−2)，但工具实际验证的只是最后一步加法；乘法中间值由模型提供。选中技能不是使用 add 的前提，因为程序始终提供 add。Skill 补充任务做法，工具权限由程序控制。
